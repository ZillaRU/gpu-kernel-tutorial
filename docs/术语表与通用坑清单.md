# GPU Kernel 教程：术语表与通用坑清单

> 这页做两件事：
> 1. 把整套教程里高频出现的术语统一口径；
> 2. 把跨章节反复出现的通用坑收成一份 checklist。

---

## 一、统一术语表

### 1. Thread

最小软件线程抽象。你可以把它理解成“执行同一段代码、但处理不同数据位置的最小单位”。

### 2. Warp / Wavefront

硬件调度基本单位。

- NVIDIA 常见是 **warp = 32 lane**；
- AMD 常见是 **wavefront = 64 lane**。

最重要的直觉：

> 同一 warp/wavefront 内的分支分歧会让硬件效率下降。

### 3. Block

一组可协作的线程。常见特征：

- 能共享片上共享存储；
- 能在 block 内同步；
- 是 grid 的组成单元。

### 4. Grid

一次 kernel launch 的全部 block/program 的集合。

最重要的直觉：

> grid 太小，GPU 根本铺不满；grid 合理，硬件才有机会隐藏延迟。

### 5. Program（Triton）

Triton 里的一个工作单元。教学上常可以把它理解成“更接近 block 的抽象入口”。

### 6. Tile

把大问题切成的小块。常见有：

- 输出 tile；
- A/B 输入 tile；
- K 维推进 tile。

### 7. `BLOCK_M / BLOCK_N / BLOCK_K`

矩阵/分块 kernel 中最常见的三个分块参数：

- `BLOCK_M`：输出 tile 行数；
- `BLOCK_N`：输出 tile 列数；
- `BLOCK_K`：K 维单次推进深度。

### 8. `num_warps`

Triton 中用于控制并行度和资源分配的关键参数。不要把它理解成“越大越快”的按钮。

### 9. `num_stages`

通常用来描述流水/预取深度。它优化的是 **load 与 compute 的重叠**，但会增加资源占用。

### 10. Occupancy

活跃 warp/wave 相对理论上限的比例。

正确理解：

> 它是一个重要信号，但不是唯一优化目标。

### 11. Coalescing

全局内存访问合并。连续 lane 访问连续地址时，硬件更容易用少量事务完成读取。

### 12. Bank Conflict

共享存储/LDS 中，多个 lane 同时打到同一个 bank，导致访问被串行化。

### 13. L2 Locality

相邻 program/block 访问相近全局地址时，更可能复用仍在 L2 中的数据。

### 14. Fusion

把多个本来分开的操作合到一个 kernel 中，主要目的是减少中间结果 HBM 往返。

### 15. Arithmetic Intensity

```text
Arithmetic Intensity = FLOPs / Bytes
```

用来粗略判断算子更像 compute-bound 还是 memory-bound。

### 16. Compute-bound

主要受算术吞吐限制的工作负载。常见优化方向：

- Tensor Core / MFMA 路径；
- inner-loop hygiene；
- tile 形状。

### 17. Memory-bound

主要受内存带宽和数据搬运限制的工作负载。常见优化方向：

- fusion；
- 向量化加载；
- locality；
- 更好的 reduce 设计。

### 18. Latency-bound

主要受 launch overhead、任务太碎、并行度不够等问题限制的工作负载。

### 19. Split-K

把 K 维拆给多个 block 并行计算 partial sum，再做规约。适合 grid 太小但 K 很大的场景。

### 20. Persistent Kernel

少量常驻 worker/block 在 kernel 内循环取活，而不是反复 launch 很多小任务。

### 21. Stream-K

通过更细粒度地拆分 K 工作来改善尾波和负载均衡的问题。

### 22. Tensor Core / MFMA

矩阵乘专用硬件路径：

- NVIDIA 常见说 Tensor Core；
- AMD 常见说 MFMA。

核心直觉：

> 很多高性能 GEMM，本质是在尽可能让编译器/硬件走到这条路径上。

### 23. Safe Softmax

先减 `max` 再做 `exp/sum` 的稳定 softmax 写法，用于防止溢出。

### 24. Online Softmax

Flash-Attention 中常用的在线维护 `max` 和 `sum` 的 softmax 组织方式。

### 25. Skeleton

教程里的“最小正确骨架”。

它不是最终高性能实现，而是：

- 地址对；
- mask 对；
- dtype 路径对；
- 能作为后续调优起点。

## 二、通用坑清单（强烈建议反复对照）

下面这份清单，几乎横跨所有章节和算子。

---

### 坑 1：地址表达写反

最经典的是 GEMM 里把 stride 方向写反。

检查方法：

- A 的地址是不是 `m * stride_am + k * stride_ak`；
- B 的地址是不是 `k * stride_bk + n * stride_bn`；
- 输出是不是 `m * stride_cm + n * stride_cn`。

### 坑 2：边界 mask 漏掉

常见于：

- `K` 不是 `BLOCK_K` 整倍数；
- `N` 不是 `BLOCK_N` 整倍数；
- softmax / norm 最后一段尾块。

经验规则：

> 先写对 mask，再谈去掉分支、追性能。

### 坑 3：低精度 reduce / accumulator

常见错误：

- GEMM 累加器用 FP16；
- softmax / norm 的 reduce 还在低精度；
- 长链条累加完全不做 `fp32` 保护。

### 坑 4：把 occupancy 当唯一目标

occupancy 低不等于一定有问题；occupancy 高也不等于一定快。

你真正该问的是：

- 为什么低；
- 低是否真的在限制吞吐；
- 提高它会不会换来更高寄存器/SMEM 压力。

### 坑 5：一上来就乱调 `num_warps`

很多问题根本不在 `num_warps`，而在：

- tile 不合理；
- 布局不合理；
- reduce 设计错误；
- 中间结果往返过多。

### 坑 6：把 fusion 当银弹

fusion 的确很值钱，但它主要值钱在 **省 HBM 往返**。

如果融合后：

- 寄存器爆炸；
- occupancy 掉很多；
- 可维护性大幅恶化；

那么它未必值得。

### 坑 7：把平台差异写成“固定参数差异”

正确表达应该是：

> 平台差异先影响执行粒度、矩阵路径、流水和资源压力，再影响参数空间。

不要写成：

```text
NVIDIA 永远用 X，AMD 永远用 Y
```

### 坑 8：把“接口长得像 CUDA”误判为“这一定是 NVIDIA 平台”

特别是在 PyTorch + ROCm 环境下，这类误判非常常见。

### 坑 9：RoPE 公式没错，但 layout 假设错了

RoPE 最容易踩的不是旋转公式，而是：

- pair 到底怎么配；
- cos/sin 的索引怎么对齐；
- 模型训练时到底用的哪种布局。

### 坑 10：Flash-Attention 忘记同步缩放 `acc`

很多人会更新 `m_i` 和 `l_i`，但忘记在 running max 变化时同步缩放累加器。

这是典型“公式看懂一半”的错误。

### 坑 11：Split-K 只看并行度，不看规约代价

Split-K 提升并行度的同时，也会带来：

- partial sum 写回；
- atomic 或 second-pass reduction；
- 数值路径变化。

### 坑 12：Persistent Kernel 只看概念，不看 ROI

Persistent 很高级，但不代表所有平台、所有任务都一定更快。

要先确认你真的是：

- launch 太碎；
- 任务不均；
- grid 小而短。

### 坑 13：benchmark 没有 warmup / synchronize

这会把：

- JIT 编译；
- autotune；
- 异步调度；
- 首次缓存效应；

混进结果里。

### 坑 14：verify 在 benchmark 后面做

正确顺序应该是：

```text
先 verify
再 benchmark
```

### 坑 15：一次改很多变量，最后不知道谁起作用

这是优化过程中最常见的管理问题，不是技术问题。

经验规则：

> 一轮只改一个主变量。

### 坑 16：结果回退了却不回滚

性能回退还继续往前叠改动，会让后续分析越来越混乱。

## 三、最常用的出手顺序（简版）

如果你遇到一个慢 kernel，建议先按这个顺序自检：

1. **地址、mask、dtype 路径是否正确**；
2. **它更像 compute-bound、memory-bound 还是 latency-bound**；
3. **该先动哪一层：Tier 1/2/3/4/5**；
4. **verify 是否通过**；
5. **benchmark 是否规范**；
6. **这一轮是否只改了一个主变量**。

## 四、建议怎么使用这页

这页最适合三种用法：

### 用法 1：读每章前先扫一遍术语

避免同一个词在脑中含义漂移。

特别是：

- 地址表达；
- mask；
- reduce dtype；
- benchmark 顺序。

它非常适合当 reviewer 的快速检查表。
